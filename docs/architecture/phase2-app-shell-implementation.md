# Phase 2 Avalonia shell implementation handoff

Status: implemented shell gate; native platform and release qualification remain deferred.

`src/UnifiDownloader.App` is a .NET 10 executable using Avalonia 12.1.2. `Program.Main` starts the Avalonia desktop lifetime for ordinary launches. The `--deterministic-smoke` argument exits before Avalonia initialization and before Infrastructure composition, so this check opens no window, creates no staging directory, probes no tools, starts no provider or process, opens no handler, and makes no network request.

`PresentationController` is the presentation command boundary. It maps the bindable `DownloadViewModel` form to Core `DownloadRequest`, routes typed observer events through `LifecycleReducer`, marshals updates through `IUiDispatcher`, and passes only `VerifiedLocalMp4` to `ILocalFileOpener`. `ApplicationComposition` loads the explicit local `unifi-downloader.tools.json` manifest and manually wires the accepted Infrastructure adapters. Missing or invalid configuration therefore reports safe unavailable capabilities and prevents a run; no tool is downloaded or discovered remotely.

The single window contains Request, Output, Browser session, Environment, Run controls, Activity, Completion, and status regions. Request offers exactly `Metadata`, `Video`, and `Audio`. Metadata uses an internal non-publication `OutputOptions` value because Core's request shape requires output options, disables every output control, and never publishes media. Video and Audio use the output fields. The frame-rate selector is two-way bound to the typed choices `Preserve source`, `24 FPS`, `25 FPS`, and `30 FPS`, and resets to `Preserve source` on `Start New Run`.

Browser-session consent is unchecked by default. When enabled, the shell requires one supported browser kind, `Chromium`, `Chrome`, `Edge`, or `Firefox`. The shell accepts no profile path or cookie-file input. Consent and browser selection are locked during a run and cleared after success, failure, cancellation, or reset. The provider receives only the typed selection and uses the supported local browser-session option; no browser data or provider diagnostics cross the presentation boundary.

Run state is projected from accepted typed lifecycle events. The shell shows safe stages, determinate progress only for a finite fraction, indeterminate progress when active work has no fraction, bounded activity entries, and terminal completion, cancellation, or failure. Cancellation first reports `Cancellation requested` and does not claim that work stopped until a terminal result arrives. Stale, duplicate, out-of-order, and post-terminal events do not change the visible state. Missing capabilities, publication conflicts, cleanup warnings, and opener failures use safe messages without raw child output, paths, URIs, cookies, tokens, or exception details.

`Open in Browser` is independent of provider/session access. It is enabled only after a published `VerifiedLocalMp4` result reaches the view model. The Infrastructure opener resolves the opaque result, re-verifies the local non-empty MP4, creates an encoded local file URI, and asks the operating system's default handler to open it. The shell does not choose a browser and does not make a provider request. `Choose Output Folder` is configured from `Window.Opened` through Avalonia's `StorageProvider`; it allows one folder and projects only a safe local path into the editable output field. If the provider is unavailable, canceled, or returns a non-file URI, the field remains editable and the UI explains the fallback. There is no `Open Folder` action.

Structural checks verified valid XAML, stable accessible names, the required help descriptions, five output-control gates, two-way frame-rate synchronization, and state-specific `Start` disabled reasons. These checks do not qualify native Windows UI Automation, Linux AT-SPI2, Narrator, NVDA, Orca, scaling, themes, dialogs, default handlers, or screen-reader behavior. ARM64, native Wayland, distributions outside the initial Linux row, live provider/media/FFmpeg behavior, packaging, signing, updates, rollback exercise, and release readiness remain separate gates. The legacy Python application is unchanged and remains the operational rollback/reference path until those gates and owner approval pass.
